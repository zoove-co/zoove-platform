# Zoove: decisions log

Each entry: what we decided, why, and what would make us revisit. Newest at the bottom.
Status values: accepted, proposed (proceeding, needs explicit sign-off), superseded.

## D1: React Native + Expo + TypeScript for customer and trainer apps (accepted)
One codebase per app for Android and iOS. Most phones in India, and most trainers' phones, are Android,
so an iOS-only native app is not enough. Pratik's SwiftUI prototype is a design and flow reference only.
Revisit if a feature needs native code Expo cannot support (use dev builds / config plugins first).

## D2: Next.js for admin panel and website (accepted)
Already shipped before. SEO for the website. Deployed on Vercel (Pro needed before launch).

## D3: Postgres + PostGIS on Supabase, used as a database only (accepted)
Real Postgres, portable. Apps never query it directly; all data goes through our API.
Migrations live in `supabase/migrations`. No schema changes in the dashboard.
RLS is enabled on every table with no policies, as a backstop.

## D4: NestJS modular monolith as the business-logic layer (proposed, proceeding)
Matching, credits, payments, notifications and CleverTap sync need background jobs and tests.
Modules own their tables; no cross-module joins, so any module can be extracted later.
Needs Ritesh's explicit confirmation.

## D5: Own OTP login, JWT access + refresh tokens (proposed, proceeding)
No vendor auth: migrating users off a vendor later is painful, and India's DLT SMS rules favour control.
SMS provider (MSG91 or Twilio) sits behind an interface.
Needs Ritesh's explicit confirmation.

## D6: One event backbone (accepted)
Domain events are written to `outbox_events` in the same transaction as the change.
Workers fan out to notifications, invoices, CleverTap, Firebase and our own `event_log`.
Apps call a single `track()` adapter, never vendor SDKs directly in screens.

## D7: Data conventions (accepted)
UUIDv7 ids generated by the API. Money in integer paise. UTC timestamptz. Phone in E.164.
Clusters and cities referenced by id, never by name. UI strings in translation files from day one.
Migrations: never edit one that has been applied; add a new file. Every function sets `search_path`.
PostGIS types are written `extensions.geography(...)` because the CLI session does not search that schema.

## D8: Bundle identifiers (accepted)
Customer app `co.zoove.customer`, trainer app `co.zoove.trainer`. Fixed before first store release.

## D9: Hosting (accepted)
API in a Docker container in a Mumbai region. Dev, staging and production each get their own
Supabase project and API instance. Terraform and AWS ECS only when load justifies it.

## D10: Visual direction is Pratik's "Expressive Canvas" (accepted by Ritesh, 7 Oct 2026)
Customer app UI follows prototype v1: white screens, purple #4B18F8, magenta #C900D8, lavender #E8D9FF,
monochrome photography. Logic and architecture follow D1-D9, not the prototype. All colours, fonts and
spacing live in one theme file so a different direction is a swap. Pratik to confirm Option 3 is final.

## D11: UI first, on a typed mock API (accepted)
Screens call hooks, hooks call TanStack Query, queries call an `api` interface. The mock implementation
ships first; the HTTP implementation (generated from OpenAPI) replaces it. No screen imports fixtures directly.

## D12: Customer app libraries (accepted)
Expo Router, TanStack Query (server data), Zustand (UI state only), React Hook Form + Zod, i18next,
Ionicons (replaces SF Symbols), Inter (body) and Kalam (wordmark, replaces iOS-only Noteworthy), expo-image.
pnpm uses `node-linker=hoisted` (see `.npmrc`) so Metro resolves workspace packages.

## D13: Commercial settings are data, not code (proposed by Ritesh, 12 Oct 2026; Pratik to confirm)
Package prices, discounts, validity, session prices (instant, scheduled, demo) and similar offers are
records that Pratik, admins and the support team edit in the admin panel (with roles and an audit log).
The customer app only displays what the API returns, so a change shows up in the app without a release.
The app never hard-codes a price, discount or expiry.

## D14: Coach choice is "rebook a past coach", not a trainer list (proposed by Ritesh, 12 Oct 2026; Pratik to confirm)
A customer cannot browse or pick trainers for a first booking. After a completed session they can ask for
one of the coaches they have already had. If that coach is not free at that time, the system matches
another coach and tells the customer. Answers open question 1.

## D15: Trainer cancels an assigned session (proposed by Ritesh, 12 Oct 2026; Pratik to confirm)
The booking is never silently lost. It moves to a "finding a new coach" state, the customer is notified at
once, and the system looks for another coach nearby. If one accepts, the customer is notified with the new
coach. The customer can reschedule or cancel at any point. What happens when nobody accepts in time, and
any compensation, are open questions 29 to 31.

## D16: Zoove Party is a separate group-booking product (from Pratik's mockups, 14 Oct 2026; scope to confirm)
Pratik shared a "Zoove Party" flow (Drive: Zoove Prototype Images Repository / Zoove Party). It is a group fitness experience at the customer's place (Dance, Wellness, Aqua and Pilates Party), not the 1:1 session. Mockup flow: landing, choose experience, experience details, date and time, duration, number of guests, location, add-ons, trainer preference, special requests, review, payment, confirmation, event details, "get party ready" checklist.
- It is built as its own booking type with its own screens; it does not change the 1:1 booking flow.
- Everything in the mockup that looks like a business rule (prices, durations, add-ons, guest limits, trainer gender choice) is a placeholder until Pratik confirms it. See open questions 35 to 42.
- Images from Pratik (logo, service tiles, participant tiles, banners, academy cards) are bundled as app assets for now. Later, banners and tiles should come from the admin panel (D13), the same way package prices do.

## D17: API foundation: sign-in, errors, limits (built by Ritesh and Claude, 13 Oct 2026)
The first API slice is in `services/api` (identity, catalog, health). It follows D4, D5, D6 and D7.
- **Sign-in:** phone + 6-digit OTP, own implementation. The code is stored only as an HMAC hash, expires in 5 minutes, allows 5 wrong tries, then locks until a new code is requested. One new code per 30 seconds and 5 per hour per phone. Two people cannot use the same code at once (row lock).
- **Tokens:** access token is a JWT valid 15 minutes; refresh token is random, stored hashed, valid 30 days, and replaced on every use. Using an old refresh token again is treated as theft and ends all of that user's sessions.
- **New customers:** the first successful OTP creates the user with role `customer`. Blocked accounts cannot sign in.
- **Errors:** always `{ "error": { "code", "message", "details" } }` with stable codes the apps can switch on.
- **Versioning and limits:** routes live under `/v1` (health excluded). Global rate limit 120 requests a minute per address, tighter on the OTP routes.
- **Secrets:** environment variables checked at start-up; the app will not start with a short secret, and refuses a fixed test OTP in production.
- The numbers above (code length, expiry, limits, token lifetimes) are engineering defaults, not business rules. See open question 47.

## D18: Booking API: safe retries, one source of truth for rules (built 22 Oct 2026)
Addresses, slots and bookings are live in `services/api` (migration 0004).
- **Retries are safe.** Every booking carries an idempotency key. The same key returns the same booking; the same key with a different request is refused. Two simultaneous requests cannot both create a booking.
- **No double booking.** The database allows only one live booking per customer per start time, so this holds even if the code has a bug.
- **Rules live in the API only** (`src/bookings/rules.ts`): slot times, the 2-hour change window, booking horizon. The app asks the API (`canChange`, slot `available`) and never decides.
- **India time on the server.** Slots are built in Asia/Kolkata; times are stored as UTC.
- **Prices are data** (D13): `service_prices`, with a default and per-service overrides. The seed prices are Pratik's prototype numbers, not confirmed.
- **Serviceability** is "the pincode belongs to an active cluster" for now. Polygon checks come when cluster boundaries exist. Clusters stay locked until ops opens one.
- **History and events.** Every change writes a `booking_events` row and an outbox event (D6) in the same transaction.
- New bookings stay in `matching`. Coaches, matching, payments, packages and refunds are not built yet.

## D19: Cancellation, refunds and payments: direction (decided 23 Oct 2026, not built yet)
Founder direction, in plain terms:
- **Reschedule first.** A customer who cannot attend is offered a new day. Cancelling is the second choice.
- **Emergency cancellation exists.** It is a request, so ops can see why.
- **Applies to every kind of session** (single, group, party). Today the API only models single "personal" sessions.
- **A cancellation is a request with its own progress:** requested, in progress, done. The customer sees it. It is separate from the booking's own status.
- **Refunds go back to the wallet or to the original payment source**, with their own progress (started, processing, done or failed).
- **A third-party payment gateway handles money.** Recommendation: Razorpay (see open question 49 for the final pick).
- **Prices are controlled by the Zoove team in the admin portal** (per session type, and changes show in the customer app). The `service_prices` table (D13) is built for this. The real prices and refund amounts are decided later.
Engineering rules we will follow when we build it: payments and refunds are idempotent; the gateway's webhook is the source of truth for "paid" and "refunded", never the app; wallet balance is a ledger of entries, never a single editable number; every state change writes an event.

## D20: Trainer onboarding on the web first (decided 23 Oct 2026, backend built)
Trainers apply through a web page now and through the trainer app later. Both use the same API and tables.
- **Why web first:** shipping and approving a trainer app in both stores takes much longer; the team (Akash) can start onboarding trainers right away. The page goes on its own address (join.zoove.co); the landing page at zoove.co is not touched.
- **Same sign-in as the apps:** phone number and OTP (`audience: trainer` signs in without creating a customer account). An applicant has no role until approved; approval creates the `trainers` row and gives the `trainer` role.
- **Application lifecycle:** draft, submitted, in review, changes requested, approved or rejected. Every step is recorded in `trainer_application_events`.
- **Files are never in the database.** Aadhaar copy, PAN, certificates and the selfie go to private S3-compatible storage (Supabase Storage now, AWS S3 later: same code). The database keeps the storage key and the review status. Uploads pass through the API, which checks the real file type and size. Reviewers open a file through a 5-minute signed link, and every view is written to `audit_log`.
- **Sensitive numbers:** PAN is encrypted (AES-256-GCM, `PII_SECRET`) with a one-way fingerprint to stop reuse. Only the last 4 digits of Aadhaar are stored, never the full number.
- **Emails come from the outbox.** The submit and review actions write events; a background worker sends "received", "changes needed", "approved" and "rejected" emails and alerts the team. Failed emails retry with a growing delay. Provider: Resend now, replaceable (SES later).
- **Admin panel** reads the same API (`/v1/admin/trainer-applications`, `admin` role only). New applications show up by refreshing the list every few seconds; push updates can come later.
- Required today: name, date of birth, gender, email, address, specialties, experience, PAN, Aadhaar last 4, Aadhaar front and back, PAN card photo, live selfie. Certificates optional. See open questions 53-56.
